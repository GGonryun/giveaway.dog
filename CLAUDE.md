# Claude Development Guidelines for Giveaway.dog

## Project Overview

This is a Next.js 15 application for hosting and participating in giveaways and raffles. Users can either host giveaways or participate in them.

## Tech Stack

- **Framework**: Next.js 15 with App Router
- **Language**: TypeScript 5.7.2, and TypeScript 7 for the type check (see Type Check)
- **Styling**: Tailwind CSS 4.1.11
- **Database**: Prisma with PostgreSQL
- **Authentication**: NextAuth.js 5.0.0-beta.25
- **UI Components**: Radix UI primitives with custom shadcn/ui components
- **Package Manager**: pnpm (preferred over npm)

## Development Guidelines

### Code Quality & Testing

- **Always run linting**: Use `pnpm run lint` before committing changes
- **Type checking**: Use `pnpm run type-check` to verify TypeScript compilation
- **Unit tests**: Use `pnpm run test:run` before committing changes
- **Never run builds for testing**: Builds are slow and not necessary for verification
- **Prefer linting/type-check over builds** for quick verification

### File Structure & Conventions

- **App location**: The Next.js app is in `apps/web`. Paths in this file are relative to `apps/web` unless they start with `apps/`, `packages/`, `tools/`, `docs/`, `.github/` or name a root file
- **Environment files**: Put `.env.local`, `.env.prod` and `.env.preview` in `apps/web`. Next.js, Prisma and the `prisma:*` scripts read them from there. Only `prisma:reset:preview` reads `.env.preview`
- **App URL**: The app builds its absolute URLs (the provider callbacks, the email links, the invite and referral links, the Bluesky client metadata) with `environment.appUrl()` from `@giveaway/app-config/environment`. It returns `NEXT_PUBLIC_APP_URL`. When that is not set, it returns `https://` and the URL of the Vercel deployment (`NEXT_PUBLIC_VERCEL_URL`, which client code can read, or `VERCEL_URL`), and outside Vercel `http://localhost:3000`. Production sets `NEXT_PUBLIC_APP_URL` and `NEXTAUTH_URL` to `https://www.giveaway.dog`. Do not set them for Preview: each preview deployment then uses its own URL, which is the URL that the end-to-end tests open. Do not read `process.env.NEXT_PUBLIC_APP_URL` or `process.env.NEXTAUTH_URL` in the code. Auth.js reads `NEXTAUTH_URL` itself, and uses the host of the request when it is not set
- **Redis**: The app uses one Upstash Redis, which it reads from `REDIS_URL` (`packages/infra/cache/src/redis.ts`). It holds the rate limits, the caches (for example `scrapebadger:*`) and the Twitch bot token. Each environment has its own database. Production uses the production database. All preview deployments share one preview database, which production never uses. Local development uses the `serverless-redis-http` container in `compose.yaml` (`pnpm run docker:compose:up`). In Vercel, set each `REDIS_URL` for one environment only. Never give Preview the production database: a preview test run would use up production's rate limits and write fixture data into production's caches. A change to `REDIS_URL` in Vercel takes effect only in new deployments
- **Postgres**: The app reads `POSTGRES_URL` (pooled) and `POSTGRES_URL_NON_POOLING` (direct, for migrations) through the datasource in `packages/infra/db-schema/src/schema.prisma`. Each environment has its own database. Production uses the production database, and you apply its migrations by hand (`prisma:migrate:production`). Each preview deployment uses its own Neon branch of the preview database, which production never uses (see Preview database branches). Local development uses the database in `.env.local`. In Vercel, set each of the two variables for one environment only, and do not connect the production database from Vercel Storage to Preview. Never give Preview the production database: pull request code and the end-to-end tests would read and write real users' data
- **Preview migrations**: Each preview build applies the pending migrations to its database branch. The `build` script runs `tools/vercel/preview-database.sh build` before `next build`. The script does nothing when `VERCEL_ENV` is not `preview`, so production builds never migrate. It stops, and the build fails, unless both variables point at a database with the comment `giveaway-preview`. The production database never has this comment, so a wrong variable in Vercel cannot migrate production. A branch copies the comment of the preview database. On a new preview database, run `COMMENT ON DATABASE <name> IS 'giveaway-preview'` once
- **Preview database branches**: The preview database is the parent of one Neon branch for each git branch. In Vercel (Storage, the preview database, Projects), its connection to `giveaway-dog` has the Preview environment and Preview branching, with **Required** on for Preview under Deployments Configuration, and **Resource must be active before deployment** on. Before each preview build, Neon creates the branch `preview/<git branch>` from the parent when it does not exist, Vercel waits until the branch is ready, and it gives the build and the deployment that branch's `POSTGRES_URL` and `POSTGRES_URL_NON_POOLING`. A preview whose branch Neon cannot create does not deploy, and the build fails when it cannot reach its branch, because `tools/vercel/preview-database.sh` connects to it before `next build`. Every deployment of a git branch uses the same database branch. A new branch is a copy of the parent, with its data and its migrations, and its first build applies the migrations that the parent does not have. The migrations and the data of a pull request stay in its branch, and no preview writes to the parent. This setting is not in the repository, so a review does not show a change to it. This bullet is its record: change both at the same time
- **Preview branch cleanup**: Neon deletes the branch of a git branch when Vercel deletes the last deployment of that git branch, so the retention of pre-production deployments in the Deployment Retention Policy of the Vercel project decides when. Closing a pull request or deleting a git branch deletes nothing. Whatever the retention, Vercel keeps the last 10 deployments of the project, the last 20 preview deployments that are Ready, the latest preview of a branch with an open pull request and each deployment with a custom alias, so the branches of the most recent previews stay. Delete a branch sooner in the Neon console (Branches, the branch, Delete). The next deployment of the git branch creates a new branch from the parent. The Neon plan limits the number of branches of a project: at the limit, Neon cannot create the branch of a new preview, and that preview does not deploy. Keep the preview branches under the limit
- **Reset a preview database**: When a preview build fails with `P3009` (a failed migration), or after you edit a migration that a preview already applied (`prisma migrate deploy` does not apply a migration again after you edit it), reset the branch of that git branch in the Neon console: Branches, `preview/<git branch>`, Reset from parent. The branch gets the schema and the data of the parent and keeps its connection strings. Then redeploy the preview, so its build applies the migrations of the pull request again. Neon does not reset a branch that has child branches. Reset the parent when its schema no longer agrees with `main`, or when it holds data that new branches should not copy. In the Neon console, open the SQL Editor on the default branch of the preview database, as the role of its connection strings. Check that `SELECT shobj_description(oid, 'pg_database') FROM pg_database WHERE datname = current_database();` returns `giveaway-preview`, so it is not production, then run `DROP SCHEMA public CASCADE; CREATE SCHEMA public;`. It deletes every table, the data and the migration history, and keeps the comment. The first build of each new branch then applies every migration. From a checkout of `main`, `pnpm --filter web run prisma:reset:preview` does the same and also migrates the parent: put the parent's values of the two variables in `.env.preview` first. The branches that exist keep their data until you reset them from the parent
- **Workspace packages**: All code other than the routes goes in pnpm workspace packages under `packages/` (see Workspace Packages). The tooling packages are in `packages/tooling/`, and the domain packages are in the other folders of `packages/` (see Directory Structure). Create a package with a generator (see Workspace Packages). The app keeps only the route files in `app/`, `middleware.ts`, `public/`, `prisma/seed.ts` and its configs
- **Auth pages**: Located in `app/(auth)/` directory
- **Shared components**: Put a reusable component in the package of its feature, or in a design system package in `packages/ui/`. `docs/monorepo/package-graph.md` describes what each package holds
- **UI components**: Use existing shadcn/ui components from `@giveaway/ui-primitives` (`packages/ui/ui-primitives/src/`)
- **Auth components**: Put shared auth components in `packages/auth/`: `@giveaway/auth-login-ui` has the login and logout screens and the provider buttons, and `@giveaway/auth-session-ui` has the session provider and the logout button

### Environment Variables

- **Sources**: Production reads the Vercel variables with the Production target, and every preview deployment reads the Vercel variables with the Preview target (Project, Settings, Environment Variables). Local development reads `apps/web/.env.local`, which starts as a copy of `apps/web/.env.example`. Vercel sets `VERCEL_ENV`, `VERCEL_TARGET_ENV`, `VERCEL_URL` and `NEXT_PUBLIC_VERCEL_URL` itself
- **One target for each value**: Give each Vercel variable one target. Never give Preview a production value: pull request code runs on Preview, and the end-to-end tests send their own requests to it. A change in Vercel takes effect only in new deployments. The build copies each `NEXT_PUBLIC_*` value into the client code

- **App URLs**: Each preview deployment uses its own URL (see App URL)
- **`AUTH_SECRET`**: Auth.js signs the sessions with it. With the production secret, a preview could make sessions that production accepts
- **Databases and Blob store**: See Postgres and Redis. The preview Blob store is one that production does not use (#200). Uploads fail without `BLOB_READ_WRITE_TOKEN`
- **`CRON_SECRET`**: The cron and workflow routes accept `Bearer <CRON_SECRET>`, and they refuse every request when it is not set. Locally, set it to call the cron routes by hand
- **`E2E_LOGIN_SECRET`**: The same value as the GitHub Actions secret of the same name, 32 characters or more (see E2E Tests). Locally, the login test and the seed API need it
- **`E2E_ALLOW_WRITES`, `E2E_ALLOW_PUBLIC`**: The seed API writes only with `E2E_ALLOW_WRITES=1`, and makes PUBLIC giveaways only with `E2E_ALLOW_PUBLIC=1` too (see E2E Tests). PUBLIC giveaways appear on `/browse` of the preview that made them, so set `E2E_ALLOW_PUBLIC` only while tests need them. Both have no effect where the e2e gate is closed
- **Turnstile**: Cloudflare's always-pass test keys are `1x00000000000000000000AA` (site key) and `1x0000000000000000000000000000000AA` (secret key). With them, a headless browser passes the security check of the giveaway page
- **`BLUESKY_PRIVATE_KEY`, `TWITCH_EVENTSUB_SECRET`**: The tests can hold the preview keys in CI. Bluesky OAuth also needs a public HTTPS `NEXT_PUBLIC_APP_URL`
- **`DISCORD_WEBHOOK_URL`**: Without it, no preview posts to the internal alerts channel. The activation job only sends this post: without the variable, it still checks the giveaway and reschedules one that has not started, but it then logs a warning, sends nothing and marks the job `COMPLETED`. #204 can add a fake webhook so that a test can check the post
- **`INBOUND_SECRET`**: Without it, a preview sends no real email. Email sign-in, email verification and invites fail until #204 adds a fake
- **Paid services**: ScrapeBadger, Google Cloud Vision and the YouTube Data API cost money for each call. The features that use them fail on Preview until #204 adds fakes
- **Sign-in providers**: `GOOGLE_ID`, `GOOGLE_SECRET`, `DISCORD_ID`, `DISCORD_SECRET`, `TWITTER_LOGIN_APP_CLIENT_ID`, `TWITTER_LOGIN_APP_CLIENT_SECRET`, `TWITCH_CLIENT_ID`, `TWITCH_CLIENT_SECRET`, `KICK_CLIENT_ID`, `KICK_CLIENT_SECRET`, `VELORA_CLIENT_ID`, `VELORA_CLIENT_SECRET`, `LINKEDIN_CLIENT_ID`, `LINKEDIN_CLIENT_SECRET`, `TIKTOK_CLIENT_ID`, `TIKTOK_CLIENT_SECRET` and `STEAM_SECRET`. Real sign-in fails on a preview, because the providers accept only the callback URLs of production. The end-to-end tests sign in with the `e2e` provider. `STEAM_SECRET` must have a value in each environment: the Auth.js config throws without it. Locally, use apps with callback URLs on `http://localhost:3000`
- **Team integrations**: `TWITTER_TEAM_APP_CLIENT_ID`, `TWITTER_TEAM_APP_CLIENT_SECRET`, `DISCORD_BOT_TOKEN`, `DISCORD_BOT_PUBLIC_KEY`, `NEXT_PUBLIC_DISCORD_BOT_ID`, `TWITCH_BOT_USER_ID`, `NEXT_PUBLIC_TWITCH_BOT_USERNAME` and `TWITCH_BOT_REFRESH_TOKEN`. With the production bot tokens, a preview posts to real Discord servers and Twitch chats
- **`TWITCH_EVENTSUB_URL`**: The default is the app URL. Locally, set it to a public HTTPS tunnel to `/api/twitch/webhooks`
- **Add a variable**: Add it to `apps/web/.env.example` and to this section, and set it in Vercel for each target that needs it

### Authentication

- **Providers**: Supports X (Twitter), Google, Discord, and email (Inbound.new)
- **Login vs Signup**: Keep separate action files for login and signup
- **Redirects**:
  - Host users → `/app`
  - Participants → `/browse`

### Component Guidelines

- **Use existing patterns**: Look at existing components before creating new ones
- **Shared components**: Extract common UI patterns (like provider buttons, error handling)
- **Styling**: Use Tailwind utility classes, follow existing patterns
- **Accessibility**: Ensure proper ARIA labels and semantic HTML

### Form Handling

- **Multi-step forms**: Use state management for step navigation
- **Validation**: Implement client-side validation before submission
- **Error handling**: Use consistent error display patterns
- **Loading states**: Always show loading spinners during async operations

### Code Style & Formatting

- **No comments**: Don't add code comments unless explicitly requested. The one exception is a Stryker disable comment for a mutant that no test can kill (see Mutation Tests)
- **Consistent naming**: Follow existing naming conventions
- **TypeScript**: Use proper typing, avoid `any`
- **Server actions**: Use `'use server'` directive for server-side functions
- **Always format code**: Ensure proper formatting when creating or modifying files
- **date-fns**: Import each function from its own module, for example `import { format } from 'date-fns/format'`, and each locale from `date-fns/locale/<code>`. ESLint rejects imports from `date-fns` and `date-fns/locale`, except type imports: they load every function or every locale, which added up to 2.8 seconds to the import time of each test file that reached them

### UI/UX Patterns

- **Cards**: Use shadcn/ui Card components for form containers
- **Buttons**:
  - Primary actions: default variant
  - Secondary actions: outline variant
  - Destructive actions: destructive variant (especially for back buttons on hover)
- **Forms**: Multi-step forms should show progress with stepper components
- **Spacing**: Use consistent gap and padding patterns

### Common Patterns to Follow

1. **Always use TodoWrite** for task planning and tracking
2. **Read existing code** before implementing new features
3. **Extract shared components** when you see duplication
4. **Use Suspense boundaries** for components that use useSearchParams
5. **Set dynamic = 'force-dynamic'** for auth pages
6. **Handle form submission** only on final steps in multi-step forms

### Testing & Verification

- Run these commands from the repository root. The root scripts call the scripts in `apps/web/package.json` and `apps/web-e2e/package.json`
- Use `pnpm run lint` for code linting (ESLint). It runs the `lint` target of every project through Nx, then `pnpm run lint:root` for the files outside the projects (the root configs, `docs/` and `.github/`)
- Use `pnpm run type-check` for TypeScript verification. It runs the `type-check` target of every project through Nx, which reads the projects that did not change from its cache (see Type Check)
- Use `pnpm run test:run` to run all the tests one time (Vitest): server tests, property tests, component tests and snapshot tests of every package. The root `vitest.config.ts` lists them (see Workspace Packages)
- Use `pnpm run test:unit` to run only the server, property and component tests, `pnpm run test:server` to run only the server tests, `pnpm run test:property` to run only the property tests, `pnpm run test:frontend` to run only the component tests, and `pnpm run test:snapshot` to run only the snapshot tests
- Use `pnpm run test:coverage` to run the server, property and component tests and measure the code coverage
- Use `pnpm run test:property:coverage` to measure the property coverage of each package and print the report of the `Property tests` job (see Property Tests)
- Use `pnpm run test:integration` to run the integration tests against a real Postgres database in Docker (see Integration Tests). `pnpm run test:run` does not run them
- Use `pnpm run test:visual:docker` to run the visual tests in the Playwright Docker image that CI uses, and `pnpm run test:visual:docker:update` to update their reference screenshots (see Visual Tests)
- Use `pnpm run test:e2e` to run the Playwright end-to-end tests against a running app (see E2E Tests)
- Use `pnpm run test:mutation:changed` to run Stryker on the lines you changed in `packages/` since `origin/main`, and `pnpm run test:mutation <package>` to run it on a whole package (see Mutation Tests). Run `test:mutation:changed` before you push a change to `packages/`
- Use `pnpm --filter web exec vitest run --project <name>` to run one project of the app: `server`, `property`, `frontend` or `snapshot`. From the root, the project names start with the package name, for example `pnpm exec vitest run --project 'web:server'`

### Nx

- **Projects**: pnpm workspace packages under `apps/` and `packages/`. `web` is the app in `apps/web`, `web-e2e` is the Playwright tests in `apps/web-e2e`, and the `@giveaway/*` packages are in `packages/`. Their targets are the scripts in their `package.json`, and the `lint` and `type-check` targets under `nx.targets`. `nx.json` sets the cache and the inputs
- **Cached targets**: `lint`, `type-check`, `test:unit`, `test:server`, `test:property`, `test:frontend` and `test:snapshot`, for example `pnpm nx run web:lint`. A second run with no changed inputs reads the result from the cache. `lint` is defined in each `package.json` under `nx.targets` with the `@giveaway/eslint-config:lint` executor. It runs ESLint from the root on the project's folder. ESLint uses the package's own `eslint-suppressions.json` when the package has one, and the root `eslint-suppressions.json` when it does not (see Continuous Integration). Flags after `--` go to ESLint, for example `pnpm nx run web:lint -- --fix`. `type-check` is defined in `nx.json` (see Type Check)
- **ESLint in one process**: The executor has a batch implementation. Nx gives every `lint` task of a run that is not in the cache to one process, which lints the projects one after the other. Each ESLint process spends about 2 seconds to load the plugins, the config and the project graph. With one process for each project, each of the 3 `Lint` shards of a full run (83 projects) took 103s to 107s and about 5 CPU minutes on 4 CPUs. In one process it takes 35s to 42s and about 1 CPU minute. The executor runs as the ESLint CLI (it sets `process.argv[1]`), because `@nx/eslint-plugin` reads the project graph again for each file in a process that it does not know as a terminal run, such as the batch process of Nx
- **Inputs**: Each cached target hashes the files of its project, the non-test files of the workspace packages it depends on, the versions of the npm packages that they use, and the `sharedGlobals` files in `nx.json` (`.nvmrc` and the root `package.json`). No input names the CI files in `.github/`, so a change to them affects no project (see Continuous Integration). The named inputs in `nx.json` keep each tool out of the targets that do not use it:
  - `lint` hashes `default`, `^lintable` and `eslint` (the root `eslint.config.mjs`, `eslint-suppressions.json` and `tsconfig.base.json`, and the source, `package.json` and `executors.json` of `@giveaway/eslint-config`). `@giveaway/vitest-config` sets `lintable` to its `package.json` only, so a change to its source does not re-run `lint`
  - `type-check` and the `test:*` targets hash `source` (the files of the project without its `eslint-suppressions.json`) and `^runtime`. `@giveaway/eslint-config` sets `runtime` to nothing, so a change to it, to the ESLint files at the root or to an `eslint-suppressions.json` re-runs only `lint`. These changes still affect every project, and the other targets of those projects read their results from the cache
  - A package overrides a named input in `"nx": { "namedInputs": { ... } }` in its `package.json`. Check the inputs of a target with `pnpm nx show target inputs <project>:<target> --check <file>`
- **Affected projects**: `pnpm nx affected -t <target>` runs a target only for the projects that changed since `main`, and the projects that depend on them. `web-e2e` depends on `web`. A change to `pnpm-lock.yaml` affects only the projects that use the changed packages (`projectsAffectedByDependencyUpdates` is `auto`). A package that only the root tooling uses, such as ESLint or Prettier, is in no project, so a lockfile-only update of it affects no project. A full run still runs it (see Continuous Integration)
- **Dependencies**: Each npm version is written once, in the `catalog` of `pnpm-workspace.yaml`. A `package.json` writes `"<name>": "catalog:"`. Add an app dependency with `pnpm --filter web add --save-catalog <name>`. Add workspace tooling (Nx, ESLint, Prettier, Vitest and its plugins) to the root `package.json` with `pnpm add -D -w --save-catalog <name>`. A workspace package depends on another one with `"workspace:*"`. Vitest runs from the root, so its peer dependencies (`@types/node`, `jsdom`, `playwright`) stay in the root `package.json` with the same versions the app uses. Otherwise pnpm installs a second copy of Vitest, and the visual tests stop with no output. `packageExtensions` in `pnpm-workspace.yaml` gives `@hookform/resolvers` a `zod` dependency with the catalog range: it imports `zod` without declaring it, so it would otherwise get whichever `zod` pnpm hoists, and a `zod` 4 from a tool (Stryker brings one) breaks the types of every `zodResolver` call
- **Other commands**:
  - `pnpm nx show projects` lists the projects, and `pnpm nx show project web` shows the targets of one
  - `pnpm nx run <project>:<target>` runs one target, for example `pnpm nx run @giveaway/team-model:test:unit`
  - `pnpm nx run-many -t <target> --projects=tag:<tag>` runs a target for the projects with a tag, for example `--projects=tag:platform:x` or `--projects=tag:scope:sweepstakes`
  - `pnpm nx affected -t <target>` runs a target for the projects that changed since `main` and their dependents
  - `pnpm nx graph` opens the project graph, and `pnpm nx graph --file=graph.json` writes it to a file
  - `pnpm nx g @giveaway/generators:<generator>` creates a package (see Workspace Packages)
  - `pnpm nx reset` clears the cache and the project graph. Run it when `@nx/dependency-checks` or the boundary rules report a dependency that a package no longer has
- **Build**: `nx.json` defines a `build` target default that is never cached, so a build always uses the current environment variables. Vercel finds this target and builds the app with `cd ../.. && npx nx build web`
- **CI**: CI runs the targets through Nx. See Continuous Integration

### Workspace Packages

- **Location and names**: A package is in `packages/<group>/<name>` and is named `@giveaway/<name>`. `pnpm-workspace.yaml` lists `apps/*`, `packages/**` and `tools/*`
- **Shape**: A package ships TypeScript source, with no build step. `exports` in its `package.json` lists each module, for example `"./button": "./src/button.tsx"`. Do not add barrel `index.ts` files. Its tags go in `"nx": { "tags": [...] }`: a `type:` tag, a `runtime:` tag and a `scope:` tag (the first folder under `packages/`), plus `platform:<name>` for a platform plugin. See Package Types and Dependency Rules
- **Tooling packages**: `packages/tooling/` has the packages that configure the others:
  - `@giveaway/tsconfig`: the `base`, `library`, `react-library` and `nextjs` presets. A `tsconfig.json` extends one of them, for example `"extends": "@giveaway/tsconfig/library.json"`. The presets list shared type declarations in `files`, so every project that extends them sees them: `react.d.ts` (`React.PC`, in `react-library` and `nextjs`) and `scrapebadger.d.ts` (the types of the scrapebadger package, whose `package.json` points to a file it does not ship, in `library`, `react-library` and `nextjs`). It also provides `tsgo`, the TypeScript 7 compiler that the `type-check` target runs (see Type Check)
  - `@giveaway/eslint-config`: `base` has the rules and the snapshot-assertion rule. `boundaries` has `@nx/enforce-module-boundaries` as an error, with the `depConstraints` that `dependencyRules` in the same file defines, the `@giveaway/no-server-in-client` rule (`src/rules/`, see Package Types and Dependency Rules) and `@nx/dependency-checks` for each `package.json` under `packages/`. Tests, the shared test fixtures in a package's `src/testing/` and package config files (`vitest.config.ts`, `eslint.config.mjs`) may also import `type:config` packages, and `@nx/dependency-checks` ignores their imports. The root `eslint.config.mjs` uses both. The rules need the Nx project graph, which `pnpm run lint` builds when it runs the targets through Nx. `src/executors/lint/` has `lint`, the Nx executor of every `lint` target (see Nx)
  - `@giveaway/vitest-config`: `projects` defines the `server`, `property`, `frontend` and `snapshot` projects of a package (`packageTestConfig`). It also sets `TZ=UTC` and replaces `server-only` with an empty module. Its `setupFiles` option replaces the default setup, `@giveaway/testing-server/setup`; the `frontend` and `snapshot` projects add `@giveaway/testing-dom/setup` after it. `reset-modules` is the first setup file of every project (see Isolation in Frontend Tests). The `server` and `property` projects always isolate their test files. The `frontend` and `snapshot` projects use the `isolate` option, which is `false` by default. `workspace` finds the `vitest.config.ts` of each package for the root config
  - `@giveaway/testing-mocks`: the Prisma, session and `next/cache` mocks, and `/setup`, which mocks `next/cache` and resets the mocks before each test. It depends on no workspace package
  - `@giveaway/testing-server`: the default setup file of every project, which loads `@giveaway/testing-mocks/setup` and mocks `@giveaway/db-client/prisma` and `@giveaway/auth-core/config-no-providers`, the helpers that tests import (`@giveaway/testing-server/prisma`, `/session` and `/next-cache` re-export `@giveaway/testing-mocks`, `/result`, `/property` for property tests, and `/faults` for fault-injection tests) and the fixtures that tests of several packages share (`/fixtures-*`). Because it depends on `db-client` and `auth-core`, the packages that they depend on (`auth-core`, `db-client`, `db-model`, `db-schema`, `integration-model`, `util-collections`, `util-errors` and `util-types`) cannot use it: their `vitest.config.ts` passes `setupFiles`, and `auth-core` mocks Prisma in `src/testing/setup.ts` with `@giveaway/testing-mocks`. The cycle check of the boundary rules fails when one of them depends on it
  - `@giveaway/testing-dom`: the jsdom setup of the `frontend` and `snapshot` projects, with the check that fails a test file that leaves a React transition pending (see Pending transitions in Frontend Tests), and the `/test-utils` and `/stable-dom` helpers
  - `@giveaway/testing-visual`: the Vitest config (`/config`), the browser setup (`/setup`) and the `renderVisual` helpers (`/render`) of the visual tests, and `visual-docker`, which runs the visual tests of the package it is called from in the Playwright Docker image
  - `@giveaway/testing-postgres`: the Vitest config (`/config`), the global setup that starts Postgres with Testcontainers and migrates a template database (`/global-setup`), and the helpers that create and migrate databases and run the Prisma CLI (`/database`) of the integration tests. It depends on no domain package, so `@giveaway/db-schema` can use it
  - `@giveaway/testing-integration`: the setup of the integration tests (`/setup`), the client of the test database and `holdTableWrites` (`/database`), the fixtures that create hosts, sweepstakes and entries (`/fixtures`), and the database client that stops after a given write (`/faults` and the `/faults-setup` setup file, see Fault-Injection Tests)
  - `@giveaway/mutation-testing`: the Stryker options (`/stryker-options`), the Stryker plugins that load the Vitest runner and ignore `console` calls, the gate on changed lines (`/gate`), the nightly audit report (`/audit`) and package picker (`/pick-packages`), and `src/cli.ts`, which the root `test:mutation*` scripts and the **Mutation audit** workflow run with Node. It has no build step: Node runs its TypeScript directly, so its modules import each other with the `.ts` extension and use no TypeScript-only syntax such as `enum` or `namespace`
- **Domain packages**: The folders of `packages/` other than `tooling/` have the domain packages. Import them by package name, for example `@giveaway/util-errors` or `@giveaway/db-client/prisma`, never with a path into `packages/`. Each one is in `transpilePackages` in `apps/web/next.config.ts` and is a `workspace:*` dependency in `apps/web/package.json`. `apps/web/app/globals.css` has `@source '../../../packages'`, so Tailwind finds the classes that packages use. `docs/monorepo/migration-plan.md` records how the code moved out of `apps/web`
- **Prisma**: `@giveaway/db-schema` has `schema.prisma` and the migrations in `packages/infra/db-schema/src/`. Its `postinstall` runs `prisma generate`, and `pnpm --filter @giveaway/db-schema run generate` runs it again. The `prisma:*` scripts in `apps/web/package.json` find the schema through `prisma.schema` in that file, and read the env files in `apps/web`. Import the Prisma client from `@giveaway/db-client/prisma`. In a package, import the Prisma enums and types from `@giveaway/db-model`, not from `@prisma/client` (the app still imports `@prisma/client`). `@giveaway/db-model` re-exports every type of `@prisma/client`, and the enums and `Prisma` as named values, because Vite cannot re-export the values of a CommonJS module with `export *` and the visual tests run in Vite. When you add an enum to the schema, add it to `packages/infra/db-model/src/index.ts`. Its test fails until you do. `@giveaway/db-client` and `@giveaway/db-model` have an implicit Nx dependency on `@giveaway/db-schema`, so a schema change affects every project that uses the generated client
- **Adding a package**: Run a generator from the root. It writes `package.json` (tags, `lint` and `type-check` targets, `exports`, scripts and dependencies), `tsconfig.json`, `vitest.config.ts`, a first module in `src/` with a test in `src/__tests__/`, adds the package to `transpilePackages` in `apps/web/next.config.ts`, formats the files and runs `pnpm install`. The new package passes lint, type check and tests as it is. Pass `--module <name>` to name the first module (the package name by default), and `--dry-run` to see the files first:
  - `pnpm nx g @giveaway/generators:model <name> --directory <folder>`, and the same with `util`, `server`, `ui` and `feature`. `<name>` has no `@giveaway/` scope, for example `referrals-model`, and `<folder>` is a folder of `packages/`, for example `participants`. Its first segment is the `scope:` tag
  - `pnpm nx g @giveaway/generators:platform-slot <platform> <slot>` creates `@giveaway/<platform>-<slot>` in `packages/integrations/<platform>/`, with the type of the slot and a `platform:<platform>` tag. The slots are in "Platform plugins" in `docs/monorepo/package-graph.md`. For a `task-*` slot, add the package to the registry package of the same name in `packages/tasks/`
  - Then add the package to the `dependencies` of each package that imports it (`workspace:*`), and to `apps/web/package.json` when a route imports it, and run `pnpm install`
- **Vitest config of a package**: `vitest.config.ts` exports `defineConfig(packageTestConfig())`, or passes `setupFiles` (see `@giveaway/testing-server`) or `isolate: true` (see Isolation in Frontend Tests). The root `vitest.config.ts` adds the four projects of each package that has one, named `<package>:server`, `<package>:property`, `<package>:frontend` and `<package>:snapshot`. A package with tests has `test:*` scripts for the projects it uses, so Nx and CI run them

### Package Types and Dependency Rules

- **Types**: Each package has one `type:` tag. `@nx/enforce-module-boundaries` fails on an import of a package whose type the importer may not import:

  | Type      | Contents                                                     | May import                                 |
  | --------- | ------------------------------------------------------------ | ------------------------------------------ |
  | `util`    | Helpers with no React and no server code                     | `util`                                     |
  | `model`   | Zod schemas, types, constants and pure functions             | `model`, `util`                            |
  | `server`  | Server actions, queries, API clients, jobs and webhooks      | `server`, `model`, `util`                  |
  | `ui`      | Presentational components and hooks that call no server code | `ui`, `model`, `util`                      |
  | `feature` | Pages and components that call server actions                | `feature`, `ui`, `server`, `model`, `util` |
  | `config`  | tsconfig, ESLint and Vitest presets, test setup and fixtures | `config`, `model`, `util`                  |
  | `app`     | `apps/web` and `apps/web-e2e`                                | everything                                 |
  | `tool`    | `tools/generators`                                           | `server`, `model`, `util`                  |

  `dependencyRules` in `packages/tooling/eslint-config/src/boundaries.mjs` defines this table. `ui` never imports `server`, and `server` never imports `ui`

- **Tests may import `type:config` packages**: tests, the fixtures in `src/testing/` and the `vitest.config.ts`, `vitest.visual.config.ts` and `eslint.config.mjs` of a package may also import `type:config` packages, such as `@giveaway/testing-server`. Runtime code may not
- **No cycles**: the rule also fails on a dependency cycle between packages. The project graph counts `devDependencies`, so a test dependency can close a cycle too (see `@giveaway/testing-server`)
- **Only the exports**: a package imports another package by name, and only the modules in its `exports`. The rule fails on a relative import into another package, so a feature never reaches into the internals of another feature. To share a module, add it to the `exports` of its package, or move it to a `model` package
- **Runtime tags**: `runtime:server` (every `server` package; each module that is not a server action imports `server-only`), `runtime:react` (`ui` and `feature`) or `runtime:isomorphic` (`util`, `model`, `config`, `tool`). A `model` or `util` package does not depend on React
- **Client and server code**: the `@giveaway/no-server-in-client` ESLint rule follows the imports of each module that begins with `'use client'`, and of the modules it reaches, and fails when it reaches a module of a `runtime:server` package. It skips `import type` and imports whose names all have `type`, and stops at a `'use server'` module, because a client bundle gets only a reference to a server action. It also fails on a `'use client'` module in a `runtime:server` package. It works on files, not packages: a `feature` package may still import a server action or render a Server Component. To fix a report, move the constant or schema to a `model` package or use `import type`
- **Dynamic imports**: `checkDynamicDependenciesExceptions: ['@giveaway/**']` turns off the rule's check for static imports of lazy-loaded packages. Tests import packages with `await import()` after `vi.resetModules()`, and one such import makes the whole project edge dynamic. No code uses `next/dynamic` with a package

### Type Check

- **Compiler**: The `type-check` target runs TypeScript 7, the native compiler, as `tsgo --noEmit --singleThreaded` in the project folder. `@giveaway/tsconfig` depends on it (`"typescript": "catalog:native"`, from the `native` catalog of `pnpm-workspace.yaml`) and provides the `tsgo` bin (`packages/tooling/tsconfig/tsgo.mjs`), so every project that extends a preset has `tsgo`. The other packages keep TypeScript 5.7 (`"typescript": "catalog:"`) for ESLint, Next.js and editors, because TypeScript 7 has no JavaScript API. `next build` and `next typegen` load it to read `tsconfig.json`, but do not check types with it (see The Next.js build)
- **Target**: The `type-check` target default in `nx.json` defines the command. Each project has `"type-check": {}` under `nx.targets` in its `package.json`, and no `type-check` script: Nx would run the script instead of the command, through `pnpm run`, which adds about 1.6s to each task. The generators add the target. `web` sets its own command, `next typegen && tsgo --noEmit --singleThreaded` (see The Next.js build)
- **The Next.js build**: `next build` does not check types: `apps/web/next.config.ts` sets `typescript.ignoreBuildErrors`, and the build prints `Skipping validation of types` (#316). The `type-check` target checks them instead, with TypeScript 7. The check of the build ran TypeScript 5.7, so it could disagree with `tsgo` (#314), and it took 42s and 46s of the 94s and 95s of `next build` on two preview deployments with the build cache (commits d111c66 and bcf2822), and 46s of 1m37s in production (2dface4). On the preview deployment of #316, the build skipped it in 0.2s, and `next build` took 40s (31s to compile, against 39s and 41s before):
  - **Route types**: Before `tsgo`, the target of `web` runs `next typegen`, which writes the files that `next build` generated for its own check: `next-env.d.ts`, and the route types and `validator.ts` in `apps/web/.next/types`. `validator.ts` checks the exports of each page, layout and route handler against its route, for example the `params` of a route handler. `tsgo` reports a wrong one as an error in `.next/types/validator.ts` that names the route file. Without `next typegen`, the `type-check` target of `web` missed these errors. The generated files are not in git, so Nx does not hash them. `next typegen` loads `next.config.ts`, so `withWorkflow` runs the workflow builder, which writes `apps/web/app/.well-known/workflow/` (not in git either) and takes about 5s of the 7s of `next typegen`
  - **A type error**: It fails the `Type check` job, so `Checks` fails. The pull request cannot merge, and a commit of `main` builds but never gets the production domains (see Production deploys). A preview deployment with a type error builds and deploys, and `e2e.yml` tests it
  - **Not chosen**: Next.js 16.4.0 can check types with the `tsc` CLI (`experimental.useTypeScriptCli`), and so with TypeScript 7: the check of `web` took 11s locally (see #316). It needs TypeScript 7 as the `typescript` of `apps/web`, and pnpm would then resolve the `typescript` peer of `@auth/prisma-adapter`, `@prisma/client`, `prisma` and `workflow` to it (see Peers). It would cost those 11s on each deployment only to stop a preview with a type error, which `Checks` already keeps out of `main`
- **One project**: `pnpm nx run <project>:type-check`. Errors name the files of the project that has them, and fail its task. A package also reports the errors of the workspace packages it imports, because it checks their source
- **Threads**: `pnpm run type-check` and the `Type check` job run 4 tasks at a time (`--parallel=4`), and each `tsgo` runs on one thread. With the default threads of `tsgo`, each process used every CPU, and a full run took 4m38s instead of 2m25s
- **Peers**: Do not give another package `catalog:native`. pnpm can resolve a `typescript` peer to TypeScript 7: in a package that depends on it, and in a package that does not list `typescript` itself. typescript-eslint would then load TypeScript 7 and fail. `@giveaway/eslint-config` lists `typescript` for this reason. After a dependency change, check that `pnpm-lock.yaml` resolves no peer to `typescript@7.0.2`
- **TypeScript 7 options**: TypeScript 7 removed `baseUrl`, so `paths` in `apps/web/tsconfig.json` start with `./`. It checks side-effect imports by default (`noUncheckedSideEffectImports`). The `nextjs` preset turns this off, because `apps/web` imports `globals.css`, which has no type declaration
- **Times**: In a 4-CPU cloud session, a full run with no cache takes 1m39s to 2m25s, and `web` takes 17s, of which `next typegen` takes 7s. With TypeScript 5.7 and a `tsc --noEmit` script in each package, it took 16m06s, and `web` took 52s. In CI, the TypeScript step of the 2 `Type check` shards took 36s and 40s in a full run with no cache (run 37569311941), against 45s to 93s in each of 8 shards before (run 37542957150). #248 compares the other options: project references, one program for every package and `isolatedDeclarations`

### Frontend Tests

- **Location**: Put tests in the package of the code they test, in a `__tests__/` folder next to the code: server and model tests named `<name>.test.ts`, component and hook tests named `<name>.test.tsx`, and snapshot tests in a separate file named `<name>.snapshot.test.tsx`. Put fixtures that tests of other packages share in `src/testing/<name>.ts` and export them as `./testing/<name>` (for example `@giveaway/util-errors/testing/application-error`)
- **Projects**: Files that end in `.snapshot.test.tsx` run in jsdom (the `snapshot` project). Other files that end in `.test.tsx` run in jsdom (the `frontend` project). Files that end in `.property.test.ts` run in Node (the `property` project, see Property Tests). Other files that end in `.test.ts` run in Node (the `server` project), except the files that end in `.integration.test.ts` (see Integration Tests)
- **Setup**: `@giveaway/testing-dom/setup` (`packages/tooling/testing-dom/src/setup.ts`) loads the jest-dom matchers, cleans up after each test, stubs `matchMedia`, `ResizeObserver`, `IntersectionObserver` and `scrollIntoView`, and checks after each test file that no React transition is pending: it starts a transition and fails the file when the transition cannot end. It names the first file that leaves a transition pending in its worker, and stays quiet in the later files of that worker until the transitions end (see Pending transitions). `@giveaway/testing-server/setup` mocks Prisma, the session and `next/cache` in every project that uses the default setup
- **Isolation**: The `frontend` and `snapshot` projects run without file isolation (`isolate: false`). Each Vitest worker runs many test files of a package in one process and one jsdom window, so a file does not pay again for a new process, a new jsdom and the npm packages. The tests of `ui-primitives` take 12s instead of 58s (frontend) and 5s instead of 44s (snapshot). The `server` project keeps isolation: it gains little, and 87 server test files in 20 packages fail without it
- **What each file still gets**: `@giveaway/vitest-config/reset-modules` is the first setup file of every project. Before each test file, it resets the modules, so the file imports its own copy of the workspace modules with its own `vi.mock` factories, and the setup files and the modules that they import run again. Without it, a component that one file loaded keeps the mocks of that file in the next file, and `@giveaway/testing-mocks/setup` (mocks and their reset before each test) applies only to the first file of each worker. After each test file, it restores the real timers, the stubbed globals and the stubbed environment variables
- **What the files of a worker share**: the jsdom `window` and `document` (cookies, `localStorage`, the URL, properties set on `window`) and the npm packages, which load once for each worker. A test that changes one of them resets it, as the tests of `sidebar` (the cookie) and `use-url` (the URL) do. To give each test file of a package its own process again, pass `packageTestConfig({ isolate: true })`
- **Pending transitions**: React, which loads once for each worker, holds every async transition of the worker until all of them end. A test that leaves one pending keeps every later transition of the worker pending, and a later file that waits for one to end fails. The usual cause is a loading-state test whose mocked server action returns `new Promise(() => {})` to a component that calls it through `useProcedure`. Return a promise that the test resolves in `act` after its assertions instead, as the loading tests of `delete-confirmation-modal` and `use-create-template` in `@giveaway/sweepstakes-actions-ui` do
- **Order**: Without isolation, a test that depends on an earlier file fails only in some orders. Run the tests of a package in other orders, in one worker, so that all its files share one process, with `pnpm nx run <package>:test:frontend -- --maxWorkers=1 --sequence.shuffle.files --sequence.seed=<number>`
- **Libraries**: Use `@testing-library/react` with role queries (`screen.getByRole`) and `@testing-library/user-event` for interactions. Use `renderHook` for hooks
- **Snapshots**: Use `toMatchSnapshot()` for representative states, only in `.snapshot.test.tsx` files. ESLint rejects snapshot assertions in other test files. Keep snapshots deterministic: freeze time with `vi.setSystemTime`, mock `Math.random` and id generators, and do not snapshot Radix-generated ids
- **Mocks**: Mock `next/navigation`, `next/link`, `next/image`, `next-auth/react` and server actions with `vi.mock` in the test file
- **Pattern**: See `packages/ui/ui-primitives/src/__tests__/button.test.tsx` and `packages/ui/ui-primitives/src/__tests__/button.snapshot.test.tsx`

### Continuous Integration

- **Workflow**: `.github/workflows/ci.yml` runs on each pull request, on each push to `main` and by hand (`workflow_dispatch`). It has no schedule, so it spends no runner minutes when nothing changes
- **Checks**: Each check is its own job, so the jobs run at the same time and each one reports its own status: `Lint` (ESLint, with the boundary rules, on the projects and on the files outside them: the root configs, `docs/` and `.github/`, then `pnpm run format:check` on the whole repository), `Type check` (TypeScript), `Server tests` (Vitest server tests, with coverage), `Property tests` (Vitest property tests, with coverage, and the property coverage report, see Property Tests), `Frontend tests` (Vitest component tests, with coverage), `Snapshot tests` (Vitest snapshot tests), `Visual tests` (screenshots in Chromium), `Integration tests` (Vitest integration tests against Postgres in Docker), `Mutation tests` (Stryker on the changed lines, see Mutation Tests), `E2E tests` (Playwright against the Vercel preview of the pull request, see E2E Tests) and `Coverage` (merges the coverage of all the tests, and of the server and the frontend tests on their own). The steps of `Lint` run even when an earlier one fails, so one run reports every lint and format failure. Each of these checks runs as one or more shards (see Shards)
- **The `Checks` job**: It waits for every other job except `Coverage` and `Badges`, which only track the tests (see Badges), and passes only when all of them passed. `E2E tests` runs only on a pull request, so on `main` it is skipped, and `Checks` accepts that. It also runs when a job failed or was cancelled, and then fails, so it never shows as skipped. Merge a pull request only when `Checks` passes. Require `Checks`, and no other job, in branch protection, so the shards and the checks can change without a change there: add a new check to the `needs` of `Checks`. On `main`, its last step also sets the commit status `Vercel - giveaway-dog: Checks`, which Vercel waits for (see Production deploys). Do not rename the job or the status: branch protection waits for a check named `Checks`, Vercel waits for a status of that exact name, and neither ever gets a renamed one
- **Speed first**: The repository is public, so the standard GitHub runners cost nothing. CI is laid out for the shortest wall time, not for the fewest runner minutes. The jobs run on `ubuntu-24.04-arm` (4 CPUs), except `Visual tests`, which runs on `ubuntu-latest` (x64, 4 CPUs) because the visual references come from the x64 Playwright image (see Visual Tests). If the repository becomes private again, every minute counts toward the plan, and the standard runners have 2 CPUs: check the layout again, and the number of tasks of each job (see Tasks and workers)
- **Shards**: Every check runs as one or more jobs at the same time, named `<check> <shard>/<shards>`: `Lint` and `Frontend tests` in 3, `Type check`, `Server tests` and `Snapshot tests` in 2, and `Property tests`, `Visual tests` and `Integration tests` in 1. `Mutation tests` has no shards, because it mutates only the changed lines. To change the number of shards of a check, change its `matrix.shard` list. `.github/scripts/select-shard-projects.mjs <target> <shard> <shards>` gives each shard every Nth project, sorted by name, of all the projects with the target, and keeps only the ones that the run selects (affected or all). A project stays in the same shard from run to run, so each shard keeps its own Nx cache (the `id` input of `.github/actions/nx-cache`). A shard with no selected project stops after the selection, and on a pull request that changes no project, before the setup (see Changes that affect no project). Only `Lint 1/3` runs `lint:root` and Prettier. In one job on `ubuntu-24.04-arm`, a full run took 9m41s for the type check of all 245 projects, 3m44s for the frontend tests, 3m11s for ESLint, 2m53s for the server tests and 2m20s for the snapshot tests (run 37496372527, before the frontend and snapshot tests ran without isolation). With the shards, in a full run in which Nx read no task from its cache (run 37542957150), the step that runs the check took 64s to 70s in each `Lint` shard (ESLint), 70s to 75s in each `Server tests` shard, 49s in `Property tests`, 49s to 57s in each `Frontend tests` shard and 45s to 47s in each `Snapshot tests` shard. The longest single task sets a floor for its shard. In that run, the longest task (the critical path in the Nx summary of the shard) took at most 13s (`Frontend tests`), 12s (`Property tests`), 8s (`Server tests` and `Snapshot tests`) and 6s (`Lint`). With the settings of Tasks and workers, in the same kind of run (run 37565555111), the step took 21s to 23s in each `Lint` shard (in one ESLint process since #255), 68s to 71s in each `Server tests` shard, 40s in `Property tests`, 40s to 44s in each `Frontend tests` shard and 31s to 32s in each `Snapshot tests` shard, and in one worker the frontend tests of `ui-primitives` took 16s and no snapshot task took more than 7s. In the same kind of run after #248 (run 37569311941), the TypeScript step took 36s and 40s in the 2 `Type check` shards, and the longest type check took 7s. Before, with 8 shards and TypeScript 5.7, it took 45s to 93s in each shard, and the type check of `web` took 31s. Before #246, the frontend tests of `ui-primitives` took about 66s and its snapshot tests about 40s (see Isolation in Frontend Tests). GitHub runs at most 20 jobs of the account at the same time. A run starts 15 shards, `Mutation tests` and, on a pull request, `E2E tests` (which waits for the preview), then `Coverage`, `Checks` and, on `main`, `Badges`, so one run fits, and two runs at the same time queue jobs
- **Tasks and workers**: `Server tests`, `Property tests`, `Frontend tests` and `Snapshot tests` run 4 Nx tasks at a time (`--parallel=4`, one for each CPU; Nx runs 3 by default), as `Type check` does (see Threads in Type Check). `Frontend tests` and `Snapshot tests` also run each package in one Vitest worker (`--maxWorkers=1`; Vitest starts one worker for each CPU but one), so all the files of a package share one worker (see Order and Pending transitions in Frontend Tests). Their files run without isolation, so each worker sets up its own jsdom and loads the npm packages again: one worker for each package, and one package for each CPU, do the least work. Measured in #253 on `ubuntu-24.04-arm`, every project of each shard with no cache, two runs of each setting: a `Frontend tests` shard took 38s to 39s instead of 50s to 53s, and a `Snapshot tests` shard 30s to 31s instead of 43s to 46s, with about 28% less CPU time. The server and property tests keep isolation, so each test file starts its own process whatever the number of workers. They gain 4% to 8% from the 4th task, and one worker made `Server tests 2/2` slower. 6 tasks were no faster than 4, beyond the noise, and used up to 58% more memory. `Lint` runs every project of its shard in one ESLint process (see ESLint in one process in Nx), so `--parallel` does not change it, and ESLint's own `--concurrency` made each shard 1.1 to 9 times slower, because each of its threads loads the plugins and the config again. In two full runs of the whole workflow, one before and one after the change (37565423162 and 37565555111), each `Frontend tests` and `Snapshot tests` job took 8s to 27s less, and the runner time of the four test checks went from 829s to 696s. With `Type check` in 2 shards since #248, the step of each `Server tests` shard (68s and 71s) is now the longest. Local runs keep the defaults of Nx and Vitest
- **Nx in CI**: On a pull request, each job runs its target for the affected projects (`nx show projects --affected`) of its shard: each project that changed since the commit of `main` that the pull request starts from (`nrwl/nx-set-shas`), and each project that depends on it. A change to a package that only `web` depends on runs the targets of that package, `web` and `web-e2e`, and a change to no project (for example, only Markdown files at the root) runs no tests. A change to a file that only `lint` uses (see Inputs in Nx) affects every project, but the other targets read their results from the Nx cache. A change to the CI files in `.github/` affects no project, so it runs no target and the jobs skip their setup (see Changes that affect no project): to test it on every project, run the workflow by hand on the branch (see Full runs). On a push to `main`, each job runs its target for every project of its shard (see Full runs), so the badges count every test of each commit of `main` (see Badges). `Lint 1/3` also runs `pnpm run lint:root` on every run, because the files outside the projects belong to no project and `nx affected` cannot select them
- **Changes that affect no project**: Before its setup, each job runs `.github/actions/changes`, which reads the changed files with git alone. When a pull request changes only root Markdown files and files in `docs/`, `.github/` and `.claude/`, which belong to no project and which no Nx input names, the job skips the setup, the Nx cache and the selection. `Lint 1/3` still sets up the project for `lint:root` and Prettier, and checks that `nx show projects --affected` is empty. When Nx finds an affected project there, the job fails: remove the pattern of the changed file from the action. A push to `main` and a manual run never skip. So the pull request of a change to `.github/actions/setup` runs the setup only in `Lint 1/3`: to test it in every job, run the workflow by hand (see Full runs). No planning job runs before the others to skip the shards with no selected project: it needs the same setup to build the project graph, and every job would wait for it, which takes longer than the setup of the shards it skips (#252)
- **Full runs**: A push to `main` and a manual run (Actions tab, **Run workflow**, on any branch) use `pnpm nx run-many -t <target>` for all the projects. The repository is public, so the extra runner minutes cost nothing. A full run catches a failure that the affected runs miss, such as a dependency that the project graph cannot see. The tasks whose inputs did not change read their results from the Nx cache, with their reports and test counts, unless the manual run has **Run every task again instead of reading its result from the Nx cache** checked (the `skip-cache` input, which sets `NX_SKIP_NX_CACHE`). Check it to test a change to the CI files on every project. `Mutation tests` is the exception: on a push, it still mutates only the lines that changed since the last commit of `main` with a successful run, which `nrwl/nx-set-shas` finds through the GitHub API (so the workflow has the `actions: read` permission)
- **Nx cache in CI**: `.github/actions/nx-cache` starts a small server (`server.mjs`) that gives the cache to Nx through the Nx remote cache API (`NX_SELF_HOSTED_REMOTE_CACHE_SERVER`). `actions/cache` keeps the files of the server in `.nx/ci-cache`, for each job (or shard) and branch, with a fallback to `main`. The action only restores the cache: the last step of each job saves it with `actions/cache/save`, also when a check of the job failed, because `actions/cache` saves nothing after a failure. Nx stores only the results of the tasks that passed, so the next run reads them and runs only the failed and changed tasks again. The server deletes the entries that no run used for 7 days. Nx cannot use a copy of its own local cache folder, because its cache database is tied to the machine. A re-run on the same commit reads `lint`, `type-check` and the tests from the cache
- **Paths in CI**: Each project writes its Vitest reports to `.vitest-reports` in its folder. `.github/scripts/collect-vitest-reports.mjs` copies them to `.vitest-reports` at the root, and the `Coverage` job merges them with `vitest.coverage.config.ts` into `coverage/all/coverage-summary.json` at the root, and the reports of the server and the frontend tests on their own into `coverage/server` and `coverage/frontend`. A merge counts the files of each package that ran the tests it merges. That config has only the coverage options, and the root `vitest.config.ts` merges it, so the options stay in one place. The merge uses only the coverage in the reports. It cannot match the test files to the projects, because each package runs its tests under the project names `server`, `property` and `frontend`, so it runs with `--passWithNoTests`. It needs no project and no workspace package, so `Coverage` does not set up the project: it installs only `vitest` and `@vitest/coverage-v8`, at the versions in `pnpm-lock.yaml`, and links them as `node_modules`. Keep `vitest.coverage.config.ts` free of imports from the workspace. Each shard of `Server tests`, `Property tests` and `Frontend tests` uploads its reports as an artifact for the `Coverage` job and reports the test results. Each Vitest job (`Server tests`, `Property tests`, `Frontend tests`, `Snapshot tests`, `Visual tests` and `Integration tests`) also writes the JSON report of each project to `.vitest-results/<kind>.json` in its folder (an output of the cached targets, so a cache hit restores it), and `.github/scripts/count-tests.mjs <kind> <shard>` adds up the passed, failed and skipped tests of the shard into the `test-results-<kind>-<shard>` artifact, also when a test failed. The visual test attachments are in `.vitest-attachments` in the folder of each project that has visual tests. The Playwright report is in `apps/web-e2e/playwright-report`
- **Badges**: The badges only track the tests, and never fail CI. `Coverage` and `Badges` have `continue-on-error`, `Checks` does not wait for them, and the step of `Property tests` that reports the property coverage cannot fail its job. A failing test still fails its own job. After each push to `main` and each manual run on `main`, the `Badges` job runs `.github/scripts/badges.mjs` and adds one commit to the `badges` branch, also when a test failed. The README shows each badge with the shields.io endpoint badge of a JSON file on that branch, and links it to `history.csv`:
  - `coverage`, `server coverage` and `frontend coverage`: the merged line coverage of all the tests, the server tests and the frontend tests (the outputs of `Coverage`). `property coverage`: the property coverage of the `model` and `util` packages (the output of `Property tests`, see Property Tests). Each one is red below 50%, yellow below 80% and green above
  - `server tests`, `property tests`, `frontend tests`, `snapshot tests`, `visual tests` and `integration tests`: the number of tests that passed (green), or that failed (red) when the job failed, from the `test-results-*` artifacts. A job that failed with no failed test (a test file that does not load, a screenshot that does not match) shows `failing`
  - `mutation tests`: the mutants that the gate killed on the lines that the push changed (the `checked`, `killed` and `failed` outputs of `Mutation tests`), or the number that survived. A push that changes no line of `packages/*/src/` keeps the last value
  - `e2e tests`: the result of the `E2E tests` status on the last commit of the pull request that the push merged. `e2e.yml` tests preview deployments, not production, so this is the closest result for the code of `main`. The job reads it with the `pull-requests: read` and `statuses: read` permissions. A pull request with no E2E result yet (still running) keeps the last value
  - `history.csv` gets one row for each run: the date, the commit of `main`, each value and the link to the run, whose job summaries have the details by package. A badge whose job did not run or did not report keeps its last value and leaves its cells empty. A badge with no value yet shows `no result yet`, because shields.io shows `resource not found` for a missing file. When the columns change, the script rewrites the file with the new columns
  - The job adds to the branch and never replaces it, so its history keeps every value. Runs on `main` never overlap (see the `concurrency` group of the workflow), so their pushes cannot conflict. It is the only job with the `contents: write` permission, and it runs only the code of `main`, because the other jobs run the code of pull requests with read access only. Do not edit the `badges` branch by hand
- **Vercel previews**: The `ignoreCommand` in `apps/web/vercel.json` runs `tools/vercel/ignore-build.sh`. It skips a preview build when every file that changed since the last deployment of the branch (`VERCEL_GIT_PREVIOUS_SHA`) is a Markdown file at the root, a file in `docs/`, `.github/` or `.claude/`, a test, a snapshot, a screenshot or a Vitest config. It always builds production, the first deployment of a branch, and a change to `apps/web-e2e`. For a skipped preview, the `E2E tests` job tests the last preview of the same app (see CI in E2E Tests). The build does not check types, so a preview deploys even when `Type check` fails (see The Next.js build in Type Check)
- **Production deploys**: Vercel builds each push to `main` as a production deployment while CI runs. It moves the production domains (`www.giveaway.dog`, `giveaway.dog`, which redirects to `www`, and `giveaway-dog.vercel.app`) to that deployment only after `Checks` passes on the same commit, and builds nothing again when it moves them. A commit whose `Checks` fails never gets the domains, and the last deployment that passed keeps serving them. When a push cancels the pending CI run of an earlier push (see the `concurrency` group of the workflow), the earlier commit never gets a passing `Checks` and never goes live, and the newer one does:
  - **The setting**: Deployment Checks in the settings of the Vercel project (`giveaway-dog`, team Charity Games) requires the commit status `Vercel - giveaway-dog: Checks` for production deployments only, so preview deployments do not wait. It is not in the repository, so a review does not show a change to it. This bullet is its record: change both at the same time
  - **The status**: The last step of `Checks` sets it with `gh api` on each run on `main`: `success` when every job passed, and `failure` otherwise. A job's check run is not a commit status, so the job sets the status itself. The step does not use `vercel/repository-dispatch/actions/status`, which Vercel suggests: that action looks up its own job by the ID of the run, which every job of the run shares, so in a workflow with several jobs it reports the result of the first job of the run, not its own. A re-run of the failed jobs of a run on `main` runs `Checks` again and sets the status again. Anyone with write access to the repository can also set the status through the API
  - **No side effects in the build**: A production build runs with the production variables before `Checks` passes, also for a commit that never goes live. Never add a step to the build that writes to production, such as `prisma migrate deploy`. Apply the production migrations by hand (see Postgres). `tools/vercel/preview-database.sh build` does nothing outside a preview build (see Preview migrations)
  - **Held deployments**: Each deployment has its own `*.vercel.app` URL, which serves it before it gets the domains. Vercel Authentication protects these URLs (`ssoProtection` is `all_except_custom_domains`), so only members of the Vercel team and requests with `VERCEL_AUTOMATION_BYPASS_SECRET` reach a held deployment. Keep this protection on
- **Package manager in CI**: pnpm 10 with `--frozen-lockfile`, the same as the Vercel build. `.github/actions/setup` restores `node_modules` from the cache, with a key from `.nvmrc`, `pnpm-lock.yaml`, `pnpm-workspace.yaml` and `schema.prisma`. Only when it misses, the action restores the pnpm store (with a key from `pnpm-lock.yaml`), runs `pnpm install` and saves both right away, so a check that fails later does not lose them. After a dependency change, commit `pnpm-lock.yaml`
- **ESLint baseline**: `eslint-suppressions.json` (at the root, with paths relative to the root) records the errors that existed when ESLint was added. A package that moved with recorded errors has its own `eslint-suppressions.json`, also with paths relative to the root. The `lint` executor gives it to ESLint with `--suppressions-location` when the file exists. New errors fail the check. Do not add entries to these files to hide new errors
- **After you fix a recorded error**: Run `pnpm run lint:prune` from the root and commit the changed `eslint-suppressions.json` files. It runs every `lint` target through Nx with `--prune-suppressions`, one at a time, because several projects share the root file. If you do not, ESLint stops with exit code 2
- **Formatting**: The `Prettier` step of `Lint 1/3` runs `pnpm run format:check` (`prettier --check .`) on the whole repository, not only the affected projects, because Prettier also checks the files that belong to no project (the root files, `docs/` and `.github/`). It runs even when an ESLint step fails, so one run reports both. The log names each file that is not formatted. Run `pnpm run format` and commit the result
- **Package boundaries**: The `Lint` job enforces the package types, the cycles and the client and server rule (see Package Types and Dependency Rules). Fix a report in the code. Do not add suppressions for these rules
- **Mutation audit**: `.github/workflows/mutation-audit.yml` runs Stryker every night on three packages picked at random, one job per package, and opens an issue for each package with survivors or a failed run (see Mutation Tests). It is not part of `Checks`

### Property Tests

- **What they are**: A property test states a rule that must hold for every input, and [fast-check](https://fast-check.dev) generates the inputs (100 runs per property by default). Use them for rules about draws, eligibility, entry values and other logic where one wrong result costs trust. Write the property from the product rule, not from the current code
- **Location**: Put them in the `__tests__/` folder next to the code, named `<name>.property.test.ts`. The `property` project runs them, and the `server` project leaves them out, so `pnpm run test:run`, `pnpm run test:property` and the `Property tests` job run them. Add `"fast-check": "catalog:"` to the `devDependencies` of the package
- **Scripts**: Every `model` and `util` package has `"test:property": "vitest run --project property --passWithNoTests"`, so its property coverage is measured even when it has no property tests. The `model` and `util` generators add it. A package of another type gets it with its first property test: add the script, and add `--project property` after `--project server` in its `test:unit`. A package with property tests runs them in `test:unit`. Without the script, CI does not run its property tests
- **Writing a test**: Run the property with `assertProperty` (or `assertAsyncProperty` for `fc.asyncProperty`) from `@giveaway/testing-server/property`, not with `fc.assert`, so the environment variables below work. Put the ID of the rule in the test title, for example `it('[DRAW-002] toUniquePrizeDraw never picks the same user twice', ...)`. When the code under test uses `Math.random`, generate a seed with `randomSeed` and stub `Math.random` with `seededRandom(seed)`, so the seed of the run reproduces the whole failure. See `packages/winners/winners-server/src/__tests__/selection.property.test.ts`
- **Slow properties**: Vitest stops a test after 5 seconds. When the 100 runs of a property take seconds, give its `describe` a timeout that grows with the number of runs, so `FC_NUM_RUNS` raises it too: `describe('...', { timeout: (propertyParameters().numRuns ?? 100) * 200 }, ...)`. `packages/integrations/discord/discord-bot/src/__tests__/verify.property.test.ts` does this, because each of its runs signs and verifies a body with `tweetnacl`, which takes about 40ms in JavaScript. With the default timeout, its properties failed on a slow CI runner
- **A known bug**: When a property fails because of an open bug, mark it with `it.fails` and name the issue in the title, for example `(fails until #134 is fixed)`. Change it to `it` in the pull request that fixes the bug
- **Coverage**: The `Property tests` job runs `test:property` with coverage, and `.github/scripts/property-coverage.mjs` reads `coverage/property/coverage-summary.json` in each package that ran and writes a report to the job summary: the line coverage of the property tests over the `model` and `util` packages (the pure code that property tests are for, the `property coverage` badge and its column of `history.csv`), a table of the packages with property tests and their coverage, and the `model` and `util` packages with no property tests, largest first. The report never fails the job (see Badges). Packages of other types with property tests are in the table, but do not count toward the total. On a pull request, only the affected packages run, so the total is partial. Keep the job in 1 shard: the total and the badge need every package in one report. `pnpm run test:property:coverage` runs it on every package (about a minute)
- **CI**: The seed is not pinned, so each run tries new inputs. A failure prints the seed, the path and the shrunk counterexample, for example `{ seed: -311437948, path: "0:0:0:0", endOnFailure: true }` and `Counterexample: [...]`
- **Reproduce a failure**: Pass the seed and the path from the failure, and select the test with `-t`: `FC_SEED=-311437948 FC_PATH=0:0:0:0 pnpm exec vitest run --project '@giveaway/winners-model:property' weighted-rolls.property -t 'DRAW-001'`. `FC_NUM_RUNS=10000` runs more inputs, to search for a rare failure locally

### Integration Tests

- **What they are**: An integration test calls a procedure against a real Postgres database instead of the Prisma mock. Write one when the database behavior is the point: unique constraints, cascades, transactions, locks, raw SQL, migrations, and two requests that run at the same time. Test the logic around the queries with mocked server tests, and do not convert the mocked tests
- **Location**: Put them in the `__tests__/` folder next to the code, named `<name>.integration.test.ts`. The `server` project leaves them out, so `pnpm run test:run` and the other `test:*` scripts do not run them and do not need Docker
- **Run them**: `pnpm run test:integration` runs the `test:integration` target of every project through Nx, and `pnpm --filter <package> run test:integration` runs one package. They need Docker. In a Claude Code cloud session, start Docker first with `dockerd > /tmp/dockerd.log 2>&1 &`. The target is not cached
- **How they work**: `@giveaway/testing-postgres/global-setup` starts one Postgres container for each run with Testcontainers and applies the migrations of `@giveaway/db-schema` to a template database with `prisma migrate deploy`. `@giveaway/testing-integration/setup` copies the template to a new database for each test file, sets `POSTGRES_URL` to it before the test file is imported, and empties every table before each test. It mocks the session (`signIn` from `@giveaway/testing-server/session`) and `next/cache`, but not `@giveaway/db-client/prisma`, so the procedures use the real database. The image is `postgres:17-alpine`; keep it on the major version of the production database. Set `INTEGRATION_POSTGRES_IMAGE` to try another image
- **Add them to a package**: Add a `vitest.integration.config.ts` that exports `defineConfig(integrationTestConfig())` from `@giveaway/testing-postgres/config`, a `"test:integration": "vitest run --config vitest.integration.config.ts"` script, and `@giveaway/testing-integration` and `@giveaway/testing-postgres` to the `devDependencies`. See `packages/winners/winners-server`
- **Writing a test**: Create the rows with `@giveaway/testing-integration/fixtures` (`createHost`, `createSweepstakes`, `createEntry`, `createEntries`) or with `db` from `@giveaway/testing-integration/database`, call the procedure, check its result with `expectOk` and `expectFailure` from `@giveaway/testing-server/result`, and read the rows back with `db`
- **Concurrent requests**: Two calls in `Promise.all` often run one after the other, so a race shows up only sometimes. Run them inside `holdTableWrites(table, { writers }, run)` from `@giveaway/testing-integration/database`: it locks the table in `EXCLUSIVE` mode, so the requests can read it but wait when they write to it, and it releases the lock when `writers` requests are waiting (or after 3 seconds). Every request then reads the same state before any of them writes. See `packages/winners/winners-server/src/procedures/__tests__/roll-prizes.integration.test.ts`
- **A known bug**: When a test fails because of an open bug, mark it with `it.fails` and name the issue in the title, for example `(fails until #135 is fixed)`. Change it to `it` in the pull request that fixes the bug
- **Migrations**: `packages/infra/db-schema/src/__tests__/migrations.integration.test.ts` applies the full migration history to an empty database, and fails when `prisma migrate diff` finds a difference between the migrated database and `schema.prisma`. When it fails, add a migration for the schema change
- **Coverage**: The integration tests do not count toward the coverage report
- **CI**: The `Integration tests` job runs the `test:integration` target of the affected projects (see Nx in CI). The `ubuntu-24.04-arm` runner has Docker

### Fault-Injection Tests

- **What they are**: Tests that check what happens when something fails at the edges: a third-party call times out or fails, the function stops in the middle of a job, two cron runs overlap, or a provider delivers the same webhook twice. They cover the job processors of `/api/jobs/process` (`task-jobs`, `sweepstakes-jobs`, `automation-server`), the Twitch and Discord webhooks (`twitch-bot`, `discord-bot`) and the X picker workflow (`x-picker-workflow`)
- **Where**: The third-party faults are server tests named `<name>.faults.test.ts`, with the Prisma mock. The crashes, overlapping runs and duplicate deliveries are integration tests (`<name>.integration.test.ts`), because only a real database shows the final state
- **Faults**: `fakeNetwork()` from `@giveaway/testing-server/faults` replaces `fetch`, so the real API clients and SDKs handle each fault. `network.json(matcher, body)` and `network.on(matcher, response)` answer a request, and `network.fault(matcher, fault)` fails it. A matcher is a URL prefix with an optional method (`'POST https://api.x.com/2/tweets'`), and the route added last wins. `network.requests(matcher)` lists the requests. `FAULTS` lists the faults: `timeout` (the server never answers, and the request ends only when the client aborts it), `rate-limit` (429 with no retry time), `rate-limit-retry-after` (429 with the retry time of `retryAfterTime()` in `Retry-After`, `x-rate-limit-reset`, `ratelimit-reset` and the body), `server-error` (500), `malformed-body` (200 with JSON that cannot be parsed) and `network-error` (`fetch` rejects with `TypeError: fetch failed`). For a call mocked at the module level, `faultError(fault)` returns the error that a client throws
- **Time**: Fake `setTimeout`, `clearTimeout` and `Date` (`vi.useFakeTimers({ toFake: ['setTimeout', 'clearTimeout', 'Date'] })`), and run the call with `settleWithin(promise)`. It advances the fake clock in steps up to the 300 seconds of the cron's `maxDuration`, so the retries of an SDK take no real time, and it throws `The call did not finish within 300 seconds` when the call hangs. Do not fake `setImmediate`. Prisma does not work with fake timers, so the fault tests use the Prisma mock
- **What a fault test checks**: Each test file has a table of the third-party calls of each job, and a test without faults for each call that proves the call is reached. For each fault, the run finishes, the job records the failure (`FAILED` or `PENDING`), nothing else is written and the next job of the run still runs. For a transient fault (`TRANSIENT_FAULTS`: every fault but `malformed-body`), the job runs again later: `PENDING` with a later `runAt`, no earlier than the retry time of a 429 that sends one. A token refresh that fails for a transient fault keeps the integration connected
- **Crashes**: Add `'@giveaway/testing-integration/faults-setup'` after `INTEGRATION_SETUP` in the `setupFiles` of `integrationTestConfig`. It replaces `@giveaway/db-client/prisma` with `crashableDb`, which counts the writes. `crashes.afterWrites(n)` stops the function right after write `n`: the write is saved, then that call and every later database call throw `SimulatedCrash`, so no `catch` can record anything (`n = 0` stops before the first write). `crashAtEveryWrite({ setup, run, recover, state })` runs the job once without a stop, then for each write sets up the data again, stops after that write, calls `recover` (to make the job runnable again), runs the job again and compares `state` with the clean run. It returns the mismatches. Record third-party effects in `state` as happened or not: a call made just before a stop can happen again, which is expected
- **Overlapping runs**: Run two processors inside `holdTableWrites` (see Integration Tests), so both read the same pending jobs before either writes
- **Duplicate deliveries and workflow steps**: The webhook tests send the same signed request twice. Workflow steps are plain functions in tests (`'use step'` is not compiled), so a test calls a step twice to model the workflow running it again after a stop. The Discord test mocks `start` from `workflow/api` to run the workflow in the test
- **A known bug**: Use `it.fails` and the issue number in the title, as in Integration Tests. In a fault table, `it(...knownBug(title, issue), fn)` adds `(fails until #N is fixed)` to the title and marks the test `fails` when `issue` is set. Each table has a `bugs` entry per call and expectation. Remove the entry in the pull request that fixes the bug

### Visual Tests

- **What they do**: Each visual test renders a component in a real Chromium browser (Vitest browser mode with Playwright), takes a screenshot and compares it with a reference PNG pixel by pixel. A change to a component, a Tailwind class or a theme token that changes how it looks fails the `Visual tests` check
- **Location**: Put visual tests in a `__tests__/` folder next to the code, named `<name>.visual.test.tsx`. The references go in `__tests__/__screenshots__/<name>.visual.test.tsx/`. Each project with visual tests has a `vitest.visual.config.ts` that uses `visualTestConfig` from `@giveaway/testing-visual/config`, and `test:visual` scripts. The root `test:visual*` scripts run them in every project. `pnpm run test:run` does not run visual tests
- **Writing a test**: Use `renderVisual` and `THEMES` from `@giveaway/testing-visual/render`. Render each test in the light and the dark theme. Then call `await expect.element(root).toMatchScreenshot()`. For a component in a portal (a dialog, a popover), take the screenshot of the portal element, for example `page.getByRole('dialog')`. See `packages/ui/ui-primitives/src/__tests__/button.visual.test.tsx`
- **Keep them deterministic**: Use fixed data. Do not use the current date, random values or images from the network. `@giveaway/testing-visual/setup` loads the Figtree font and turns off animations and transitions. `visualTestConfig` also loads `apps/web/app/globals.css` as a setup file, for the theme, and runs Tailwind with `apps/web` as its base, so every project gets the CSS of the app. The Nx project graph cannot see this link, so the `test:visual` target default in `nx.json` names `apps/web/app/globals.css` as an input: a change to `globals.css` runs the visual tests of every package that has them, on a pull request too. When `visualTestConfig` reads another file from `apps/web`, add it to the same `inputs` list. `test:visual` is not cached
- **The references come from the Playwright Docker image**: The pixels depend on the browser version and the fonts of the operating system, so a screenshot from your own browser does not match. The `Visual tests` job runs the `test:visual:docker` target of the affected projects, which runs them in `mcr.microsoft.com/playwright` for the Playwright version in `pnpm-lock.yaml`, on an x64 runner like the **Update visual references** workflow. Docker pulls the image only when a project with visual tests is affected. Only commit references that were made in that image, in one of these ways:
  - `pnpm run test:visual:docker:update` runs the tests in the same image on your machine and writes the new references. Use `pnpm run test:visual:docker` to only compare. These scripts need Docker on Linux, because they use your `node_modules`. In a Claude Code cloud session, start Docker first with `dockerd > /tmp/dockerd.log 2>&1 &`
  - The **Update visual references** workflow (Actions tab, or `workflow_dispatch` through the GitHub API, on your branch, not on `main`) takes new references in the same image, commits them to the branch and starts CI again on that commit
- **When `Visual tests` fails**: The job log and the job summary list each screenshot that changed, with the number of pixels that differ. The `visual-changes-<shard>` artifact has the actual screenshot and a diff image (changed pixels in red) for each one. To see them in a session, run `pnpm run test:visual:docker` and open the files in the `.vitest-attachments/` folder of the project. Then decide if each change is intended:
  - Intended (you changed how the component looks on purpose, or you added a visual test): update the references (see above). Open the new PNG files and the old ones (`git show HEAD:<path>`) and confirm that they show only what you meant to change
  - Not intended (for example, a change to a shared component or a theme token changed a component you did not mean to change): fix the code. Do not update the references to make the check pass
- **Run without Docker**: `pnpm run test:visual` uses the Chromium of your Playwright install. It is useful while you write a test, but expect small text differences against the committed references. When Chromium is not where Playwright expects it, set `VISUAL_CHROMIUM_PATH` to the Chromium binary (in Claude Code cloud sessions: `VISUAL_CHROMIUM_PATH=/opt/pw-browsers/chromium`)

### Mutation Tests

- **What they do**: Stryker changes the code one small edit at a time (a mutant), for example `a > b` to `a >= b`, `x?.trim()` to `x.trim()` or a string to `""`, and runs the tests that cover that line. A test that fails kills the mutant. A mutant that survives is a change to the code that no test notices: the line ran, but nothing checked its result. Line coverage cannot show this
- **The gate**: The `Mutation tests` job runs `pnpm run test:mutation:changed` on each pull request and each push to `main`, without shards. It finds the lines of `.ts` files under `packages/*/src/` that the pull request adds or changes (not tests, not `src/testing/`, not `.tsx`, not `packages/tooling/`), and runs Stryker on those lines only, with the tests of their package. It fails when a mutant on a changed line survives (`Survived`) or no test runs its line (`NoCoverage`). Mutants on lines you did not change never fail it. It writes the number of mutants it checked, killed and failed to its job outputs, for the `mutation tests` badge (see Badges). It takes seconds for a small change
- **Reading the result**: The job summary has a row per package and a table of the mutants that failed: the file and line, the mutator, the replacement (the code Stryker put in place of the original) and the status. When the job fails, the `mutation-report` artifact has the HTML report, which shows each mutant in the source. Locally, `test:mutation:changed` prints the same summary and writes the reports to `reports/mutation/<package>/`
- **What to do with a survivor**, in this order:
  1. Add or change a test so that it fails with the mutant in place. Usually it asserts too little: it checks that a call happened but not its arguments, checks a field but not the whole result, or misses a boundary (`>` against `>=`)
  2. If no test can kill it because the mutant cannot change behavior, change the code so the mutant cannot exist. For example, `x?.trim()` where the schema guarantees `x` is a string becomes `x.trim()`, and a default that is never used goes away
  3. Only when neither works, add `// Stryker disable next-line <Mutator>: <why no test can kill it>` above the line. The summary lists every disable comment that a pull request adds, so a reviewer can check the reason
- **Ignored code**: Calls to `console` methods are not mutated, so tests do not need to assert log text
- **Flaky results**: The Stryker Vitest runner sometimes runs no test for a mutant and reports it as `Survived`. The tool runs those mutants again, up to two times, before it reports them
- **Nightly audit**: The **Mutation audit** workflow (`.github/workflows/mutation-audit.yml`) runs every night on three packages picked at random with the date as the seed, and on demand on the packages you name (Actions tab, **Run workflow**). Each package runs in its own job: Stryker on the whole package, then the `mutation-audit-<package>` artifact with the HTML report, `report.md` and `mutation.json`. When mutants survive, the job opens or updates an issue named `Mutation audit: <package>` with the label `test:mutation`: the score of each file, a table of the survivors and the steps to fix them. When Stryker cannot run, the issue says so and points to the job log. A later audit that finds no survivors closes the issue. To work on such an issue, run `pnpm run test:mutation <package>` to see the same report, kill or remove each survivor as above, and open a pull request that closes the issue
- **Local runs**: `pnpm run test:mutation <package>` takes a package name (`winners-server` or `@giveaway/winners-server`) or its folder, and writes `report.md`, `mutation.html` and `mutation.json` to `reports/mutation/<package>/` (ignored by git). Stryker works in a copy of the package in the system temp folder, so it never changes your files

- **Tags**: Set them with the `tag` option of `test` or `test.describe`. `TAGS` in `src/helpers/tags.ts` lists them:
  - `@smoke`: the quick set. `--grep @smoke` takes under 2 minutes (about 25 seconds against `next dev`)
  - `@slow`: a test that waits longer than 30 seconds. The fixture calls `test.slow()`, which triples its timeout
  - `@mobile`: the test also runs in the `mobile` project. A test that works only on a small screen skips when the `isMobile` fixture is false
  - `@a11y` and `@security`: the kind of check
  - `@prod-safe`: the test only reads, never signs in and has no side effects. The `prod-smoke` project fails a test without it
  - `@known-bug`: `knownBug(<issue>)` adds it (see Known bugs)
  - `@quarantine`: `quarantine(<issue>)` adds it, with the issue. `grepInvert` in the config leaves these tests out of every run. Quarantine only a test that fails for a reason outside the app, and fix it in that issue
- **Shared fixture**: Import `test` and `expect` from `src/fixtures/test.ts`, never from `@playwright/test`. ESLint refuses that import in a spec. The fixture:
  - Blocks the third-party scripts of the root layout in every context of the test (see `third-party.ts` in Helpers)
  - Fails the test on an uncaught error or a `console.error` of a page. `test.use({ allowedPageErrors: [...] })` allows the strings and patterns that a test expects, as the onboarding replay test does for the request that it aborts. `PAGE_ERROR_ALLOWLIST` in `third-party.ts` applies to every test, and is empty. Fix a page error in the app instead of adding it there: this check found the hydration mismatches of `ThemeToggleButton` and `OrbitingPlatforms`
  - Applies the tags `@slow`, `@known-bug` and `@prod-safe`, and has `freshPersona` (see Signed-in tests)
- **Helpers** in `src/helpers`:
  - `known-bug.ts`: `knownBug(issue)` and `quarantine(issue)` return the details of a test, for example `test('title', knownBug(100), async ({ page }) => ...)`. Pass more details as the second argument: `knownBug(100, { tag: '@mobile' })`
  - `third-party.ts`: `blockThirdParties(context)` answers `platform.twitter.com`, `embed.bsky.app`, `connect.facebook.net`, `va.vercel-scripts.com`, `vercel.live` (the Vercel Toolbar of preview deployments, whose frame sends a CORS preflight that the deployment refuses with 400) and `/_vercel/insights/` with an empty body (an aborted script logs a `console.error`), and `avatar.vercel.sh` with a 1×1 PNG. With the avatar loaded, the avatar menu button gets its accessible name from the alt text of the image. The fixture calls it for the context of the test. Call it yourself for a context from `browser.newContext()`
  - `http.ts`: `noRedirect` (`maxRedirects: 0`), `expectSameOrigin(location)`, which fails when a `Location` header leaves the origin of `E2E_BASE_URL`, and `expectNoStackTrace(body)`, which fails on a stack trace or an internal path (`node_modules`, `.next/server`, `/var/task`, `webpack-internal`, `PrismaClient`). Use it on API and error responses: the HTML of `next dev` names chunks after `node_modules`
  - `rsc.ts`: every procedure is a Server Action. The browser POSTs to the URL of the page with a `Next-Action: <id>` header and the body `JSON.stringify([input])`. The ids change with each build, so capture them at runtime while a persona that is allowed drives the UI:
    - `captureServerAction(page, trigger, { abort })` returns `{ id, url, args }` of the first action that `trigger` sends. With `abort: true`, the action never reaches the server
    - `replayServerAction(page, action, args?)` sends it again with `fetch` from `page`, so the browser supplies the origin and the cookies of that page. Open a page of the same origin in `page` first
    - `rewriteServerActions(page, rewrite)` changes the arguments of each action in flight, and collects the responses
    - `readActionResult(response)` reads the result of the Flight response. A refusal is `{ ok: false, data: { code: 'FORBIDDEN', ... } }`, with HTTP status 200
    - Arguments that are not plain JSON (a `File`, a `Date`, a string that starts with `$`) do not replay as they are
  - `leaks.ts`: `expectNotInPayload(request, url, { name: value })` loads the page as HTML and as an RSC payload (`RSC: 1`), and fails when either one contains a value. Layouts are not an auth boundary, and the props of a client component are in the payload even when the page does not show them
  - `poll.ts`: `expectAfterReloads(page, assertion)` runs an assertion again after at most 2 reloads. `revalidateTag(tag, 'max')` serves the stale page while it revalidates, so the first reload after a write can be stale, and a missing invalidation still fails after the second reload. Do not add a mode that skips the cache to the app: it would hide the cache bugs
  - `blob.ts`: `stubBlobUploads(page)` answers the client token request to `/api/upload` and the `PUT` to `https://vercel.com/api/blob/` that `@vercel/blob` 1.1 sends, so an upload succeeds with `STUB_BLOB_URL` (the `/logo.png` of the deployment) and nothing is uploaded. It returns the list of uploads. Check both shapes again after an update of `@vercel/blob`
  - `seed.ts`: `seedApi(request)` calls the seed API with the secret: `health`, `team`, `sweepstakes`, `deleteRun` and `janitor`. The last two call again while the response has `more: true`. `seedWorkerTeam(request, testInfo)` seeds the team of the worker, `e2e-<RUN_ID>-w<parallelIndex>`, with `host` as its owner, and returns it again to the later tests of the worker
  - `personas.ts` and `user-metrics.ts`: see Signed-in tests
- **Known bugs**: When a journey finds a bug, file a bug issue, then write the test with `knownBug(<issue>)`. The fixture marks the test as expected to fail (`test.fail()`), so the run passes while the bug is open. When the bug is fixed, the test passes, Playwright reports it as a failure, and the job summary lists it under "Known bugs that pass now". Remove `knownBug` in the pull request that fixes the bug. `src/journeys/navigation/menus.spec.ts` pins #100 this way
- **Locators**: Use roles and accessible names (`getByRole`, `getByLabel`). Many controls have no name today (#100, #108, #93, #87, #90, #85). When a journey needs one, fix the issue in the app (add the `aria-label`, or link the label) instead of using a CSS selector. Use `data-testid` only where no accessible name makes sense. A test that checks that a control has a name, such as the `knownBug(100)` test, can find it with a CSS selector
- **Run locally**:
  1. Start Redis with `docker compose up -d redis serverless-redis-http`, and Postgres with `pnpm run docker:psql:local`. In a Claude Code cloud session, start Docker first with `dockerd > /tmp/dockerd.log 2>&1 &`

Copy `apps/web/.env.example` to `apps/web/.env.local` and set `POSTGRES_URL` and `POSTGRES_URL_NON_POOLING` to `postgresql://prisma:prisma@localhost:5432/prisma`, `REDIS_URL=http://default:6b58d1d2@localhost:8079`, `AUTH_SECRET`, `STEAM_SECRET` (any value: the Auth.js config throws without it), `E2E_LOGIN_SECRET` (32 characters or more) and `E2E_ALLOW_WRITES=1` (for the janitor and the teardown). Keep `NEXTAUTH_URL=http://localhost:3000`. Leave the Turnstile keys empty: without a site key, the giveaway page shows no security check
  3. Run `pnpm --filter web run prisma:migrate:local`
  4. Start the app with `pnpm dev`, then run `pnpm run test:e2e:local`. With `E2E_WEB_SERVER=1`, Playwright starts `pnpm dev` itself, or uses the server that already answers on `E2E_BASE_URL`
  - `test:e2e:local` reads `apps/web/.env.local`. Install Chromium one time first with `pnpm --filter web-e2e exec playwright install chromium`, or set `E2E_CHROMIUM_PATH` to a Chromium binary (in Claude Code cloud sessions: `E2E_CHROMIUM_PATH=/opt/pw-browsers/chromium`). The tests use `http://localhost:3000`. Set `E2E_BASE_URL` to test another deployment
  - `next dev` compiles each page on its first visit, which can take longer than the 30-second test timeout: open the pages once first, or pass `--timeout 120000`
  - In development, each procedure waits 200 to 1000 ms to simulate the network (`packages/infra/rpc-server/src/procedures.ts`). It does not wait where the e2e gate is open (`isE2eGateOpen` in `@giveaway/e2e-gate/gate`), so the delay does not slow the tests
- **Gate**: `@giveaway/e2e-gate` decides where the e2e code exists. It opens only on a Vercel preview deployment (`VERCEL_ENV=preview`, and `VERCEL_TARGET_ENV` unset or `preview`) and on the local development server (`next dev`, with `VERCEL_ENV` and `VERCEL_TARGET_ENV` unset or `development`), and only when `E2E_LOGIN_SECRET` has at least 32 characters. - **Login**: The tests sign in through the `e2e` credentials provider in `packages/auth/auth-provider-e2e/src/e2e.ts`. The app adds this provider only where the gate is open. It computes the email and never reads one from the request. It signs in no one for a persona that is not in the list below, a namespace that does not match `^[a-z0-9]{4,10}$`, or a persona without a namespace or a namespace without a persona. - **Run id**: `RUN_ID` in `apps/web-e2e/src/env.ts` is `E2E_RUN_ID`, or 6 random base36 characters when it is not set. `playwright.config.ts` imports it, so the runner sets `E2E_RUN_ID` and every worker gets the same id. In CI, `e2e.yml` makes it from `GITHUB_RUN_ID` and `GITHUB_RUN_ATTEMPT`, so each attempt of a run has its own id. Start each namespace of a run with it (see `DELETE runs/<runId>`)
- **Signed-in tests**: The `setup` project runs first, then the `personas` project, then `api`, `chromium` and `mobile` (see Projects):
  - `personas` signs in each persona with `ns = RUN_ID` and saves `src/.auth/<persona>.json`, on top of the Vercel bypass cookie. A test that only reads as a persona uses that state: `test.use({ storageState: personaState('participant') })`
  - A test that changes its user (onboarding, a role switch, a deletion) uses the `freshPersona(persona)` fixture instead (`src/fixtures/personas.ts`, in the `test` of `src/fixtures/test.ts`). It signs the page of the test in as the persona in a namespace that no other test uses (`RUN_ID`, the worker index and a counter, 10 characters), and returns `{ persona, ns, id, email }`
  - `signInAs(request, persona, ns = RUN_ID)` in `src/helpers/personas.ts` signs in any request context: it gets a CSRF token from `/api/auth/csrf`, posts to `/api/auth/callback/e2e`, and reads the user from `/api/auth/session`. The context of a page shares its cookies with `page.request`
  - Each storage state has a `user_metrics` cookie (`src/helpers/user-metrics.ts`). Without it, the metrics collector calls `trackUser` on the first page of each signed-in context. That call geolocates the request through ipwho.is on the server, and it can loop (#75)
- **Rules for persona tests**:
  - Never rename the shared `e2e-host@example.com`, change its account type or delete it. Each sign-in makes it an onboarded HOST again. If it were deleted and created again, it would get a new id, and the session of every other worker would point at a user that no longer exists (`/app` then redirects to itself)
  - A credentials sign-in always runs the `jwt` callback with `trigger: 'signIn'`, so it cannot reproduce a first sign-in through OAuth or a magic link. The mock OAuth provider of #204 covers that
  - Credentials users have no `Account` rows, so the app treats them as anonymous (`isAnonymousUser`), and they pass `doesUserHaveAllowedIdentity` only when a giveaway allows ANONYMOUS. Seed an `Account` row when a test needs a connected identity
- **Seed API**: `app/api/e2e/[...path]/route.ts` passes every request to `handleE2eRequest` in `@giveaway/e2e-server/router`. Tests use it to make states that the UI cannot make, or makes slowly, and to read rows that the UI does not show. Send the secret in the `x-e2e-secret` header and JSON in the body:
  - `GET health`: `{ environment, writes, allowPublic }`
  - `POST teams`: `{ ns, suffix, owner?, members?: [{ persona, role }], tier? }`. It creates the team `e2e-<ns>-<suffix>` (at most 20 characters) and signs up each persona as `e2e-<persona>-<ns>@example.com`, outside `MAX_USER_TEAMS`. When the team exists, it updates the tier and the roles, so a restarted worker gets its team back
  - `POST sweepstakes`: `{ ns, team, preset?, startsIn?, endsIn?, name?, description?, visibility?, slug?, tasks?, prizes? }`. `preset` is `draft`, `scheduled`, `running` (the default), `ended` or `completed`, and `startsIn` and `endsIn` are seconds from now. It creates the giveaway from the editor defaults (`toNewSweepstakesData` in `@giveaway/sweepstakes-editor-server/lifecycle`) and saves it with `applySweepstakesChanges` as the owner of the team, so it gets the same jobs as a giveaway from the editor. A `completed` giveaway also gets the `PROCESS_COMPLETION` job, as `completeSweepstakes` does. The name starts with `[e2e <ns>]`, and a slug must start with `e2e-<ns>-`
  - The giveaway page (`/browse/<id>`) returns 404 for a giveaway that the participant schema refuses, so `POST sweepstakes` always gives one the page accepts: the banner `/images/demo-sweepstakes-banner-2.jpg` of the deployment, at least one task and one prize, and a description of 3 characters or more. Without `tasks` and `prizes`, it adds one `BONUS_TASK` and one prize named `My Custom Prize`. `tasks` takes the hermetic types only (`E2E_TASK_TYPES` in `@giveaway/e2e-model/requests`: the `BONUS_*` types, `VISIT_URL`, `ASK_QUESTION`, `SINGLE_CHOICE`, `MULTIPLE_CHOICE`, `SECRET_CODE`, `SECRET_CODE_V2`, `REFERRAL_LINK` and `SUBMIT_MEDIA`). Each task is `{ type, ... }`: the fields it leaves out get the values of the editor (`toDefaultValues` in `@giveaway/task-model/defaults`), and the task schema checks the result, so `VISIT_URL` needs `href` and the question types need `question`. Each prize is `{ name, quota? }` (quota 1 by default). The API gives each task and prize a new id and returns them in `tasks` and `prizes`. `src/__tests__/round-trip.integration.test.ts` in `@giveaway/e2e-server` loads the page data of each preset and of each task type with the procedures of the page
  - `GET rows?view=team&slug=…`, `view=sweepstakes&id=…`, `view=participants&id=…` or `view=jobs&id=…`: read-only views of e2e records. A participant who is not an e2e user has `email: null`
  - `DELETE runs/<runId>`: deletes the teams whose slug starts with `e2e-<runId>` (with their giveaways) and the persona users whose namespace starts with `<runId>`. `<runId>` is 6 base36 characters, so start each namespace of a run with its run id
  - `POST janitor`: deletes e2e teams and persona users that are older than 24 hours
  - The cleanup calls delete at most 100 teams and 200 users. They return `more: true` when more are left; call them again. They delete the X picker draws of a team before the team, because `TwitterPickerDraw.pickerId` is `ON DELETE RESTRICT`
- **Seed API safety rules**:
  - When the gate is closed or the secret is wrong, every path returns 404 with an empty body. The API compares the secret in constant time and never reads it from the query string. An unknown path or method also returns 404
  - Writes also need `E2E_ALLOW_WRITES=1`; without it they return 403. A PUBLIC giveaway also needs `E2E_ALLOW_PUBLIC=1`, because PUBLIC giveaways appear on `/browse`. Giveaways are UNLISTED by default
  - It touches only users whose email matches `e2e-<persona>[-<ns>]@example.com` and teams whose slug starts with `e2e-`. It refuses a team that has a member who is not an e2e user, and it does not delete a persona user who is a member of a team outside `e2e-`. It never deletes the shared `e2e-host@example.com`
  - It has named builders only, with zod schemas that refuse unknown fields, and limits: a body of at most 64 KB, at most 10 team members, 10 tasks and 10 prizes, names of at most 80 characters and descriptions of at most 10,000 characters. It has no generic model access
  - Each call writes one log line, `[e2e] {"method","path","status","ms"}`, without the secret or the body
  - After a write, it expires the cache tags of the giveaway at once with `revalidateTag(tag, { expire: 0 })`: `sweepstakes-<id>`, `sweepstakes-<id>-privacy`, `participant-sweepstake` and `winners-leaderboard`, plus the browse lists for a PUBLIC giveaway and after a cleanup. It does not use the `'max'` profile, and the app's own reads never skip the cache
  - Its round trip runs against a real database in `packages/e2e/e2e-server/src/__tests__/round-trip.integration.test.ts`
- **Protected deployments**: `apps/web-e2e/src/setup/vercel.setup.ts` sends `VERCEL_AUTOMATION_BYPASS_SECRET` one time to get the Vercel bypass cookie. The other tests use that cookie, so the secret goes only to the deployment
- **Origin check**: `apps/web-e2e/src/setup/vercel.setup.ts` also reads `/api/bluesky/client-metadata.json` and fails when its `client_id` is not on the origin of `E2E_BASE_URL`. A deployment that builds its URLs on production or on `localhost` then stops the run before the other tests (see App URL)
- **CI**: `E2E tests` is a job of `.github/workflows/ci.yml` that runs on each pull request, and `Checks` waits for it (see The `Checks` job). It calls the reusable workflow `.github/workflows/e2e.yml` with the head commit of the pull request:
  - `.github/scripts/same-app-preview.sh <commit> 1200` waits for the `Vercel` commit status that Vercel sets on the head commit: pending while it deploys, success when the preview is ready or the ignore step skipped it ("Canceled by Ignored Build Step"), and failure when the deployment failed. A failed deployment fails the job at once, and a deployment that Vercel does not finish in 20 minutes fails it too
  - When Vercel is done, the job tests the preview of the head commit (the GitHub deployment that Vercel creates for it, with the URL of the deployment). When the ignore step skipped it, the job tests the newest of the last 50 previews (of any branch) whose commit differs from the head commit only in files that the ignore step skips, checked with `tools/vercel/ignore-build.sh`: it runs the same app and the same e2e tests. This also finds the last preview of a branch that was reset or force-pushed, which is no longer in the history of the head commit, as Vercel compares with it too. When no preview matches after 2 minutes, the job fails and says to redeploy the preview
  - The job runs Playwright from the head commit against that preview, and also sets the `E2E tests` commit status on the head commit, for the badge (see Badges)
  - On a pull request, the workflow and the scripts come from the merge commit of the pull request, which has the scripts of `main`. The job checks out `same-app-preview.sh` and `e2e-summary.mjs` from it (`.e2e-workflow`), so a branch made before a script existed still passes
  - A failed run fails `Checks`. **Re-run failed jobs** runs `E2E tests` and `Checks` again, for example after you redeploy a preview
  - A pull request from a fork gets no secrets and no preview without approval, so its `E2E tests` fails
  - To test a deployment by hand, run the **E2E** workflow from the Actions tab, on the branch of the commit, with the deployment URL
  - The job has 50 minutes: up to 20 to wait for the preview, and the rest for the tests. It sets `E2E_RUN_ID` (see Run id) and keeps 1 retry
  - The `json` reporter writes `apps/web-e2e/.playwright-results/results.json`, and `.github/scripts/e2e-summary.mjs` turns it into the job summary: the number of passed, failed, flaky, known-bug and skipped tests, and a table of each failed and flaky test, each known bug with its issue, and each known bug that passes now. The step also prints the summary in the job log, because the API cannot read a job summary: a session that reads the run through the API finds it there
  - The `playwright-report-<attempt>` artifact has the HTML report, with the trace, the video and the screenshot of each failed test (`trace` and `video` are `retain-on-failure`). Open it with `pnpm --filter web-e2e exec playwright show-report <folder>`
- **Secrets**: The workflow needs the `VERCEL_AUTOMATION_BYPASS_SECRET` and `E2E_LOGIN_SECRET` GitHub Actions secrets. Set the same `E2E_LOGIN_SECRET` in Vercel for the Preview environment only. Never set it for Production. Set `E2E_ALLOW_WRITES` and `E2E_ALLOW_PUBLIC` as Environment Variables shows

### Authentication Flow

- **Login**: Direct sign-in with provider selection
- **Signup**: Multi-step process (name → user type → provider)
- **User types**: "host" (goes to /app) or "participate" (goes to /browse)
- **No "both" option**: Users choose one path during signup

## Important Notes

- Always prioritize user experience and accessibility
- Keep components simple and focused on single responsibilities
- Follow existing patterns rather than creating new ones unless necessary
